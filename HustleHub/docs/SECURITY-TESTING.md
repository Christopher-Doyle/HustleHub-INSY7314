# HustleHub+ security testing

## Purpose and scope

OWASP ZAP is a dynamic application-security testing tool that observes and attacks a running application to identify issues that source review alone can miss. The supplied workflow is strictly scoped to the local HustleHub+ API and its temporary test database. It must never be pointed at MongoDB Atlas, GitHub, university systems, or any third-party target.

The automated API, RBAC and validation tests remain the authoritative repeatable checks for authenticated business rules. ZAP complements them; it does not replace ownership tests.

## Isolated environment

Run `npm run security:server` from the project root. This starts the HTTPS API on port `4040` with a random JWT secret and a new `mongodb-memory-server` database. Stopping the process destroys the database. It does not read or write the team Atlas database.

The API contract is [openapi.yaml](openapi.yaml). Validate it with `npm run openapi:validate`.

## ZAP workflow

Prerequisites:

- Docker Desktop with the Linux engine running
- local certificates generated by `npm run setup`
- the isolated API running with `npm run security:server`

In another PowerShell terminal run:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/run-zap.ps1
```

The script uses the official stable ZAP image and performs:

1. Baseline/passive scan of the HTTPS health entry point.
2. OpenAPI API scan using the documented routes.
3. Full active scan of the isolated local API origin.

Raw HTML/JSON reports are written to `evidence/private/zap/`, which is ignored by Git because request details can contain internal identifiers or bearer tokens. Inspect every High or Medium alert before producing a sanitised summary. Do not suppress an alert merely to make the scan green.

## Authenticated and role testing

ZAP API discovery is supplemented by `npm run test:postman` and `npm test`. Those isolated tests prove:

- missing or malformed JWTs are rejected;
- clients cannot create, update or delete Gigs;
- freelancers cannot create client bookings;
- one freelancer cannot edit or delete another freelancer's Gig;
- clients and freelancers see only their own booking/transaction scopes;
- public admin creation is rejected;
- clients and freelancers cannot access the administrator overview;
- operator objects, markup, unexpected fields and malformed IDs are rejected;
- authentication, Gig mutation and booking rate limits return controlled `429` responses.

## ZAP run — 2026-10-11

The official `ghcr.io/zaproxy/zaproxy:stable` image (ZAP 2.17.0) scanned only `https://host.docker.internal:4040`. The target used a random in-memory JWT secret and a new `mongodb-memory-server` database named `hustlehub-zap`; Atlas, GitHub, university systems and public services were out of scope and were not scanned. The temporary server was stopped after scanning and port 4040 was verified closed.

The first OpenAPI scan found one genuine reliability/security-hardening issue: `GET /api/gigs?search=%00` reached MongoDB as a regular expression and returned 500. Public string query validation now rejects control characters with 400, a regression case covers `%00`, and the complete API scan reran with no alert from that condition.

Final informational observations were reviewed as accepted behavior:

- `Non-Storable Content` and `Re-examine Cache-control Directives`: the API intentionally sends non-cacheable responses to protect authenticated and dynamic data.
- `A Client Error response code was returned by the server`: controlled 4xx responses resulted from unauthenticated calls, invalid identifiers and attack payloads generated by the API scan.
- `Authentication Request Identified`: ZAP correctly recognized the documented login operation.
- `User Agent Fuzzer`: informational confirmation that varied user-agent requests were processed without a vulnerability alert.

No alert was suppressed. The final JSON reports contain zero High, Medium or Low alerts. Raw HTML/JSON reports remain under ignored `evidence/private/zap/`; only aggregate, credential-free evidence is tracked.

## Limitations

The baseline and full-origin crawls discover only unauthenticated entry points because this project is an API plus a separately served React client. The OpenAPI scan covers the documented operations without a stored JWT. Authenticated role, ownership and end-to-end business rules are therefore covered by the disposable Node and Newman suites rather than by tracked ZAP credentials. This avoids committing passwords or bearer tokens while retaining repeatable RBAC/IDOR coverage.
